# Deploying Datix: Render (backend) + Vercel (frontend)

This project is split into two independently-deployable pieces:

```text
.
├── app.py, cleaning.py, chart_utils.py, analysis_utils.py, chat_service.py
├── requirements.txt, Procfile, render.yaml     → BACKEND, deploy to Render
├── templates/, static/                         → local dev only, ignore in production
└── frontend/                                   → FRONTEND, deploy to Vercel
    ├── index.html
    ├── static/css/style.css
    ├── static/js/app.js
    └── vercel.json
```

Follow these steps **in order** — the backend needs to exist before you can
point the frontend at it, and the backend needs to know the frontend's URL
before it will accept requests from it.

---

## Step 1 — Push to GitHub

```bash
git init
git add .
git commit -m "Datix: split backend/frontend for Render + Vercel"
git branch -M main
git remote add origin https://github.com/<your-username>/<your-repo>.git
git push -u origin main
```

---

## Step 2 — Deploy the backend to Render

1. Go to [Render](https://dashboard.render.com) → **New → Blueprint**.
2. Connect your GitHub repo. Render will detect `render.yaml` at the repo
   root automatically — no changes needed to root directory or build/start
   commands, those are already set.
3. When prompted for environment variables, set:
   | Variable | Value |
   |---|---|
   | `GROQ_API_KEY` | your key from https://console.groq.com/keys |
   | `ALLOWED_ORIGINS` | leave blank for now — you'll fill this in Step 4 |

   `SECRET_KEY` is auto-generated by the blueprint. `GROQ_MODEL` and
   `PYTHON_VERSION` already have sensible defaults.
4. Deploy. Once live, copy the service URL Render gives you, e.g.:
   ```
   https://datix-xxxx.onrender.com
   ```
5. Sanity check it's up:
   ```
   https://datix-xxxx.onrender.com/api/health
   ```
   should return `{"status": "ok"}`.

---

## Step 3 — Deploy the frontend to Vercel

1. Open `frontend/index.html` and set `window.API_BASE_URL` to the Render
   URL from Step 2 (no trailing slash):
   ```html
   <script>
     window.API_BASE_URL = "https://datix-xxxx.onrender.com";
   </script>
   ```
2. Commit and push this change:
   ```bash
   git add frontend/index.html
   git commit -m "Point frontend at Render backend"
   git push
   ```
3. Go to [Vercel](https://vercel.com) → **Add New → Project** → import the
   same repo.
4. Set **Root Directory** to `frontend`.
5. Framework preset: **Other** (it's static HTML/CSS/JS — no build command,
   no install command needed).
6. Deploy. Copy the resulting URL, e.g.:
   ```
   https://your-app.vercel.app
   ```

---

## Step 4 — Connect them: allow the frontend's origin on the backend

1. Back in the Render dashboard, open your backend service → **Environment**.
2. Set `ALLOWED_ORIGINS` to the Vercel URL from Step 3:
   ```
   https://your-app.vercel.app
   ```
   (Comma-separate multiple origins if you have, e.g., a preview URL too.)
3. Save — Render will redeploy the service automatically.

---

## Step 5 — Verify the connection

1. Open `https://your-app.vercel.app` in your browser.
2. Upload a CSV/Excel/JSON file. If it appears in the "Dataset Review"
   section, the frontend successfully reached the backend and the session
   cookie is working cross-site.
3. Open browser dev tools → Network tab if something fails, and check:
   - Requests to `/api/...` should go to `https://datix-xxxx.onrender.com`,
     **not** to the Vercel domain.
   - No CORS errors in the console (if you see one, double-check
     `ALLOWED_ORIGINS` on Render exactly matches the Vercel URL — including
     `https://` and no trailing slash).
   - The `Set-Cookie` response from `/api/upload` should have
     `SameSite=None; Secure`.

---

## How the connection works (for reference)

- **Frontend → Backend calls:** `frontend/static/js/app.js` prefixes every
  API call with `window.API_BASE_URL` (set in `index.html`) and sends
  `credentials: 'include'` so the session cookie travels with each request.
- **Backend CORS:** `app.py` uses `flask-cors`, restricted to whatever
  origins are listed in the `ALLOWED_ORIGINS` env var, with
  `supports_credentials=True`. Requests from any other origin are rejected.
- **Cross-site cookies:** in production (`RENDER=true`, which Render sets
  automatically), `app.py` marks the session cookie
  `SameSite=None; Secure` so browsers will accept and send it across the
  Vercel ↔ Render domains. Locally (no `RENDER` env var) it falls back to
  normal `Lax`/insecure cookies so `python app.py` still works standalone.
- **Downloads:** the CSV/Excel/JSON/Parquet export buttons in `index.html`
  are wired via JS (`data-format` attributes) to navigate to
  `API_BASE_URL + /api/download?...`, since a plain relative link would hit
  the Vercel domain instead of Render.

---

## Known limitations (inherent to the app, not the split)

- **Render free tier sleeps when idle.** The first request after inactivity
  can take 30–60 seconds while it cold-starts.
- **In-memory storage.** Uploaded datasets live in a Python dict in
  `app.py` (`STORE`), keyed by session cookie. They're lost if the Render
  service restarts, redeploys, or sleeps — there's no database. This is by
  the original app's design; add persistent storage separately if you need
  datasets to survive restarts.
- **One backend replica only.** Because state lives in that in-process dict,
  don't scale the Render service to multiple instances without also adding
  a shared store (e.g. Redis) — otherwise a user's session may land on an
  instance that never saw their upload.

---

## Updating the frontend URL later

If you ever redeploy the backend to a new Render URL, or add a new Vercel
preview domain:

1. Update `window.API_BASE_URL` in `frontend/index.html` (if the backend
   URL changed), commit, push — Vercel redeploys automatically.
2. Update `ALLOWED_ORIGINS` on Render (if the frontend URL changed) and
   save — Render redeploys automatically.

Both sides need to agree, or requests will fail with a CORS error.
